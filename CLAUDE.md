# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
make proto          # regenerate *.pb.go from api/**/*.proto (needs nix-shell for protoc plugins)
make proto-clean    # delete generated code
go build ./...      # build everything
go test ./...       # run tests
go test ./internal/akira-client/connection/...        # single package (the e2e tests: in-process server + real client)
go test ./internal/... -run TestName -v               # single test
TEST_DATABASE_URL="postgres://akira:akira@127.0.0.1:5432/akira" go test ./internal/auth/store/postgres/...   # Postgres store integration tests (skipped without the var; 127.0.0.1, not localhost — localhost may resolve to ::1 first and stall the connect)
go run ./cmd/akira-server                              # run server
go run ./cmd/akira-repl                                # server + stdin REPL for manual testing
go run ./cmd/akira-client -client-id <id> -connect-key <key> [-server host:port]   # run client executor
go run ./cmd/auth                                      # run auth service (registration + JWT + JWKS)
docker compose up -d                                   # full stack: Postgres + auth + akira-server + nginx (images built from one Dockerfile via --target akira-server|auth; .env supplies config, DATABASE_URL/MCP_JWKS_URL/MCP_AUTH_SERVER_URL are overridden to the compose-internal hostnames)
docker compose up -d postgres                          # local Postgres only (for go run ./cmd/... during development)
```

protoc and Go plugins come from `nix-shell` (see `shell.nix`). Proto → Go mapping is defined by the Makefile (`module=` option), not by go_package alone: `api/connection/v1/connection.proto` generates into `pkg/api/connectionpb/v1`. Never edit `*.pb.go` by hand — change the proto and run `make proto`.

Env vars (`.env` loaded via godotenv in server, repl and auth): `DATABASE_URL` (common Postgres for auth and akira-server, migrations applied at startup; required by server, repl and auth); `LISTEN` (listen address, default `":5000"`, read by both server and repl); `MAX_CONNECTIONS` (per-user limit of simultaneous client connections in the pool, default 5, 0 = unlimited; an invalid value is fatal in both server and repl). Auth service: `AUTH_LISTEN` (default `":6000"`), `AUTH_ISSUER` (default `"akira"`, becomes the `iss` claim), `AUTH_ACCESS_TTL` (default `"15m"`), `AUTH_REFRESH_TTL` (default `"720h"`), `AUTH_EMAIL_TTL` (verification code lifetime, 6 digits + 5 input attempts, default `"15m"`), `AUTH_BOOTSTRAP_USERNAME`/`AUTH_BOOTSTRAP_PASSWORD`/`AUTH_BOOTSTRAP_EMAIL` (startup user, bcrypt-hashed, immediately verified + given a connect_key; password must be ≤ 72 bytes — the bcrypt limit), `AUTH_PUBLIC_URL` (public base URL for the OAuth absolute links in RFC 8414 metadata, default `"http://127.0.0.1:6000"`), `AUTH_FRONTEND_URL` (login-form app base; `/authorize` 302s there with the OAuth params in query — empty (default) makes `/authorize` answer a JSON error, and the flow can be driven manually via `POST /authorize/confirm`), `AUTH_CODE_TTL` (authorization-code lifetime, default `"10m"`). MCP (read **only by akira-server**): `MCP_LISTEN` (second HTTP listener, default `":7000"`), `MCP_PUBLIC_URL` (this MCP listener's public base URL — builds the RFC 8707 `resource` and the `resource_metadata` URL in 401s; must share scheme+host with the address MCP clients connect to, default `"http://127.0.0.1:7000"`), `MCP_AUTH_SERVER_URL` (auth's public base URL, `authorization_servers` in the protected resource metadata, default `"http://127.0.0.1:6000"`), `MCP_JWKS_URL` (auth's JWKS, default `"http://127.0.0.1:6000/jwks.json"` — must match where auth actually listens), `MCP_AUTH_ISSUER` (default `"akira"`, must equal auth's `AUTH_ISSUER`), `MCP_TASK_TIMEOUT_MS` (default + ceiling for every task sent from MCP, including a per-call `timeout_ms` tool argument that gets capped to it, default 120000), `MCP_READ_MAX_BYTES` (file-read size limit via `read_file`, default 1 MiB); an invalid numeric value is fatal. Mail: `SMTP_HOST` (empty → verification codes are logged instead of emailed), `SMTP_PORT` (default 587), `SMTP_USER`/`SMTP_PASS`/`SMTP_FROM`. `LOG_LEVEL` (debug|info|warn|error) and `LOG_FORMAT` (text|json) are read **only by akira-server and auth**; the repl hardcodes a text handler on stderr. The `AKIRA_*`/`HOST_ID` vars previously in `.env` are not read by any code and were removed.

Deployment (docker compose): the Go services are isolated inside the compose network — only nginx (`deploy/nginx/nginx.conf`, mounted into the `nginx:1.29-alpine` container) is exposed, on port **80** over plaintext HTTP (no TLS yet, no rate limiting yet — both are planned nginx additions). Route by path: `/akira.connection.v1.ConnectionService/…` → gRPC to akira-server:5000 via cleartext HTTP/2 (h2c prior-knowledge, `grpc_pass`; akira-client connects as `-server host:80`); `/mcp` and `/.well-known/oauth-protected-resource/…` → MCP akira-server:7000; everything else → auth:6000. Compose overrides the public URLs to the nginx address (`MCP_PUBLIC_URL`/`MCP_AUTH_SERVER_URL`/`AUTH_PUBLIC_URL` = `http://localhost`), while akira-server's internal JWKS fetch goes directly to `auth:6000` over the compose network. Postgres is published on `127.0.0.1:5432` only (loopback — for local `go run ./cmd/...` and `TEST_DATABASE_URL`; not reachable from other machines). nginx resolves upstream names once at startup: after recreating a service (new IP), restart the nginx container too.

TLS termination and rate limiting are future additions to this same nginx config. Per-IP and per-route limits belong there (including on the MCP endpoint `/mcp` — tool calls run commands on user machines, so it deserves the strictest limits — and on `/oauth/register` + `/authorize/confirm` on the auth service: dynamic registration is a public unauthenticated write, and confirm is a credential-check endpoint the dummy-bcrypt timing equalization alone doesn't protect from brute force); a per-*email* limit on `/verify/resend` cannot (a proxy can't key on request bodies), so an unauthenticated caller can still trigger verification mail to arbitrary registered addresses — the remaining known gap, mitigated only by the fact that a failed resend does not burn the active code.

## Architecture

Server side of a reverse-command channel: each client holds a long-lived one-way gRPC stream (`Connect`, server→client) over which the server pushes tasks for execution on the client; the client returns results via the separate unary `SubmitResult` RPC. Connections belong to users: the client presents a short `connect_key` at registration, the server resolves it against the shared users DB and registers the pool entry under `connection_id = {user_id}:{client_id}`.

- **`api/connection/v1/connection.proto`** — the single source of truth for the wire protocol. Three RPCs: `Connect(RegisterRequest) returns (stream ServerMessage)` — one-way server→client stream; the client registers via the RPC request itself (`client_id` + `connect_key`), the server answers with `RegisterResponse` (session_id + heartbeat interval + the assigned `connection_id = {user_id}:{client_id}`) as the first stream message and then pushes `Task` (exec / read_file / write_file); `SubmitResult(TaskResult)` — unary, the client returns task results here (stamped with its `connection_id`), the server correlates them by `task_id` and rejects results from a non-owner connection; `Heartbeat(Ping) returns (Pong)` — liveness check.
- **`internal/akira-server/connection/server`** — gRPC handlers. `NewGRPCServer(pool, users)` builds the gRPC server with keepalive params (half-open TCP connections die in ~80s, so a ghost registration can't block the client's reconnect with `AlreadyExists`); all entrypoints (server, repl, tests) construct the server through it. `users` is the narrow `UserLookup` interface (connect_key → user_id + verified flag; in production backed by the shared Postgres store — `cmd` packages wrap `authstore.Store` in `storeLookup`, translating `authstore.ErrUserNotFound` into the server's `ErrUnknownConnectKey` sentinel). `Connect` validates registration (`client_id` + `connect_key` → `InvalidArgument`), resolves the user (`Unauthenticated` only for the `ErrUnknownConnectKey` sentinel — a key that will never become valid; every other lookup error, e.g. the DB being down, maps to `Internal` so the client retries instead of exiting; `PermissionDenied` for an unverified email), registers the connection in the pool under `{user_id}:{client_id}` (`AlreadyExists` if the same connection_id is already active, `ResourceExhausted` on `ErrTooManyConnections`), sends the `RegisterResponse` ack with the connection_id as the first stream message, then runs the single stream-writer loop (selects on `conn.Out()`, `conn.Done()`, `stream.Context()`; a message taken off the queue while `Done()` is closed is dropped, not sent — the pool fails all of the connection's pending tasks on connection loss). `SubmitResult` requires a non-empty `client_id` (`InvalidArgument` otherwise), routes results to the pool by `task_id` and returns `PermissionDenied` for non-owner results; `Heartbeat` echoes `Pong`.
- **`internal/akira-server/connection/pool`** — the hub other server objects use. `New(maxConnections)` (per-user limit, 0 = unlimited). `Register(connectionID, userID, info)` manage connections keyed by the composite `connection_id` — `info` is `ClientInfo{ConnectionID, ClientID, Hostname, Platform}` (ClientID filled from the connection_id suffix; hostname/platform come from the client's `RegisterRequest` and exist so the MCP layer can present machine info) — `AlreadyExists` for a duplicate id, `ErrTooManyConnections` (counted by `{user_id}:` prefix over active conns) when the user's limit is reached (`Unregister` skips if the map already holds a different, newer connection — reconnect race: in that case only the old connection's unsent queue messages are failed, since the client is back and its sent tasks may still deliver results). `Disconnect(connectionID)` atomically drops the currently registered connection under a single lock (no reconnect-race window) and returns whether one was dropped. `SendTask(ctx, connectionID, task)` is the public API: posts the task and blocks until the `TaskResult` (delivered via `HandleResult`), the task timeout (`task.timeout_ms` → `STATUS_TIMEOUT` result with nil error), caller ctx expiry/cancel (returned as a ctx **error**, never a synthetic result), or `ErrConnectionClosed` when the connection is lost — whether or not the task message left the server. Losing the connection fails **all** of that connection's pending tasks (`failPendingClient`): reconnects do not re-send tasks, so without this a task without a timeout could wait forever for a client that never returns. `pending` entries carry an owner `connection_id` plus result/error channels; re-registering a `task_id` that is still pending → `ErrTaskAlreadyPending`. `HandleResult` delivers by `task_id`, rejects non-owner results — including results with an empty `client_id` — with `ErrNotTaskOwner`, and discards unknown `task_id`s silently (e.g. results for tasks already failed on disconnect). `ClientsByUser(userID)` returns the user's active connections as `ClientInfo` (prefix filter `{user_id}:`, sorted by connection_id — the MCP layer's machine list); `ClientIDs()`/`Has()` for discovery (connection_id keyed).
- **`internal/akira-server/connection/client`** — `ClientConnection`: per-client state (session id, outgoing queue) with `Post(ctx, msg)`/`Out()`/`Done()`/`Close`. Purely outbound: result correlation lives in the pool. `Close` closes only `done` (idempotent) — the `out` channel is **never** closed, so a racing `Post` cannot panic — and returns the messages still queued so the pool can fail their waiters.
- **`internal/akira-server/connection`** (package `connection`) — shared sentinel errors (`ErrAlreadyRegistered`, `ErrConnectionNotFound`, `ErrConnectionClosed`, `ErrTaskAlreadyPending`, `ErrNotTaskOwner`, `ErrTooManyConnections`) and `NewID()` (random hex for session/task ids).
- **`internal/akira-client/connection`** — client-side connection logic: register (via the `Connect` request with `client_id` + `connect_key`), heartbeat (interval from `RegisterResponse`, 30s default; each call has a per-call deadline and the first failure tears down the session to force a reconnect), task receive loop, result outbox, reconnect loop reusing the same `client_id` + `connect_key` after disconnects. `Run` treats `Unauthenticated`/`PermissionDenied` from `Connect` as **fatal** — an invalid connect_key never becomes valid, so instead of endless retries the client exits with an error; everything else (including `Internal` when the server's DB is down) is retried. The gRPC channel uses client keepalive (30s ping / 10s timeout) so silent partitions are detected in ~40s instead of the ~15-minute TCP retransmit timeout. `submitLoop` stamps results with the `connection_id` from the ack (stored in an atomic, re-stamped on every attempt — it's stable for a user+client pair, so outboxed results stay valid across reconnects) and **drops** results on permanent `SubmitResult` errors (e.g. `ResourceExhausted` for oversized results) instead of retrying forever — otherwise one poisoned result would wedge the whole FIFO outbox. `cmd/akira-client` is a thin entrypoint: flags → `connection.Run` (`-client-id` and `-connect-key` both required).
- **`internal/akira-client/executor`** — task execution (exec via shell, read/write file). Runs on its own context bound only to `task.timeout_ms` — never to the stream.
- **`cmd/akira-repl`** — manual testing tool: starts the same gRPC server, then reads stdin commands (`list`, `use <client-id>`, `exec|read|write [client] ...`, `timeout <ms>`, `quit`).

Auth service — standalone HTTP/JSON (plain `net/http`, deliberately **not** gRPC since JWKS is HTTP by nature); registration with email verification, JWT issuance and the public key publication so consumers validate tokens autonomously. The complete end-to-end auth flow (registration, tokens, OAuth for MCP clients, machine connection) is documented in `docs/auth-flow.md`. User records (user_id, username, email, password_hash, connect_key) live in the **same Postgres** (`DATABASE_URL`) that akira-server reads — the server resolves connect_keys directly, no network hop to auth:

- **`internal/auth/token`** (package `authtoken`) — `Manager` issues access JWTs (RS256, RSA-2048 generated at startup, random `kid` per run; claims `iss`, `sub`, `jti`, `iat`, `exp`, `typ="access"`) and opaque refresh tokens (32 random bytes base64url to the client, only sha256 hash stored). `JWKS()` returns the cached public key set (`jwk` with `kid`/`alg`/`use`); `ParseAccessToken` verifies via the same JWKS path a consumer would. Keys live in memory only: after a restart the `kid` changes and all previously issued tokens become invalid — consumers should re-fetch the JWKS on unknown `kid`. Key rotation is out of scope.
- **`internal/auth/store`** (package `authstore`) — DB abstraction over users (bcrypt hashes; plaintext never reaches the store), refresh tokens, email verification codes and OAuth entities (dynamic-registration clients, one-time authorization codes), designed so one implementation closes all four interfaces. Implementations: `internal/auth/store/memory` (package `authstorememory`, mutex-guarded maps — tests and dev) and `internal/auth/store/postgres` (package `authstorepostgres`, pgxpool + embedded SQL migrations applied at startup under a `pg_advisory_xact_lock` — concurrent starts (e.g. auth + akira-server simultaneously) serialize instead of racing on check-then-apply; connect timeout 5s, startup deadline 10s; integration tests run with `TEST_DATABASE_URL`). Every multi-step state change is an atomic store method, never a handler-side sequence: `CreateUserWithCode` (user + first verification code in one transaction), `RotateRefresh` (consume the old refresh token and persist the new one in a single operation — a crash can't lose the old token *and* its replacement; refresh tokens are single-use, a replayed old token fails with `ErrRefreshNotFound`, expiry is checked store-side), `CompleteEmailVerification(ctx, userID, codeHash, connectKey)` (mark verified + consume the code + assign the connect_key atomically; the key-clash check runs **before** consumption so a clash doesn't burn the code; right code → record deleted; wrong code → attempt counted, `ErrVerificationWrongCode`; no record, expired, or `MaxVerificationAttempts` (5) exhausted → `ErrVerificationNotFound`; codes are sha256-hashed and keyed by user_id — a 6-digit code is inherently shared across users, so the record key is the user, not the code hash), `ConsumeOAuthCode` (one-time authorization code: `DELETE … RETURNING` / map-delete under one lock — exactly one concurrent exchange wins, others get `ErrOAuthCodeNotFound`; expiry checked store-side; the raw code is never stored, only its sha256 like refresh tokens). `connect_key` comes from `GenerateConnectKey`: 10 chars out of a 31-char visually-unambiguous alphabet (~50 bits, online brute-force is stopped by the proxy rate limits), rejection-sampled for a uniform distribution; globally unique, assigned only at verification. OAuth client_ids come from `GenerateOAuthClientID` (same alphabet, 26 chars). A new `SaveEmailVerification` replaces the active code and resets the attempt counter (resend). Revoke-reuse-family detection is out of scope.
- **`internal/auth/mail`** (package `authmail`) — `Sender` interface (`SendCode(ctx, to, code, ttl)`) with two impls: `smtpSender` (stdlib `net/smtp`, config from `SMTP_*` env; ctx-aware — the ctx deadline caps the connection deadline and a cancel aborts a stuck send; STARTTLS when the server offers it; refuses to send credentials over a plaintext non-localhost connection) and `logSender` (code logged — used when `SMTP_HOST` is empty, local dev mode). `New(ConfigFromEnv(), logger)` picks the impl.
- **`internal/auth/httpapi`** (package `authhttp`) — routes: `POST /register` (`{username, email, password}` → 201, emails a 6-digit verification code; 409 on taken username/email; passwords over 72 bytes → 400 — the bcrypt limit, surfaced instead of silently truncating), `POST /verify` (`{email, code}` → consumes the one-time code, marks the email verified, issues the connect_key (kept out of the response — the frontend fetches it via `/me`) and **immediately returns an access+refresh token pair** — no separate login after verification; 401 `invalid_code` for unknown email, wrong/expired/reused code — one identical answer, anti-enumeration), `POST /verify/resend` (`{email}` → **mail is sent before the new code is saved**, so a mail failure keeps the previous code valid; the new code then replaces the old one and resets attempts; unknown or already-verified email → same 200 without sending mail, anti-enumeration), `POST /token` (grant_type=password, refresh_token or authorization_code; body parsed as JSON **or** form-encoded by Content-Type — OAuth clients per RFC 6749, including mcp-go, POST forms; OAuth2-ish shapes and error codes; the password grant and `/authorize/confirm` share `checkCredentials` — bcrypt on a dummy hash for unknown users so response timing doesn't reveal account existence, unverified users get the same `invalid_grant` as wrong credentials — anti-enumeration; the refresh grant persists the replacement **before** responding, atomically via `RotateRefresh`; the authorization_code grant consumes the one-time code via `ConsumeOAuthCode`, checks client_id/redirect_uri match, verifies PKCE S256 — `base64url(sha256(verifier)) == code_challenge`; the RFC 8707 `resource` parameter is accepted and ignored), `GET /me` (Bearer access → account + connect_key), `POST /connect-key/regenerate` (Bearer access → new connect_key), `GET /jwks.json` + `GET /.well-known/jwks.json` (`Cache-Control: max-age=60`), `POST /revoke` (idempotent 204), `GET /healthz`, plus the OAuth authorization-server side: `GET /.well-known/oauth-authorization-server` (RFC 8414 metadata — absolute URLs built from `AUTH_PUBLIC_URL`; the shape mcp-go's client requires: authorization/token/registration endpoints, grants, PKCE S256, `token_endpoint_auth_method: none`), `POST /oauth/register` (RFC 7591 dynamic client registration — public clients only, no secret; redirect_uris must be https or http-on-localhost; extra fields like `resource` accepted and ignored), `GET /authorize` (validates response_type/client_id/redirect_uri-exact-match/PKCE-S256-required, then **302s to `AUTH_FRONTEND_URL` passing the query through** — the login form is a separate frontend project, auth only serves JSON; an invalid client or redirect_uri is a JSON 400, never a redirect to an unverified URL), `POST /authorize/confirm` (`{username, password, + the OAuth params}` → credential check + one-time code stored sha256-hashed with `CodeTTL` → `{location: redirect_uri?code&state}` for the frontend to navigate to; credential failure → 401 `invalid_grant`). Request bodies are capped at 1 MiB via `http.MaxBytesReader` (413 over, 400 for other malformed JSON). Same 401 `invalid_grant` for wrong password and unknown user (anti-enumeration). Store failures are logged distinctly and answered with 500 — they are **not** folded into the anti-enumeration 401s (which would hide outages from clients and monitoring alike). Tokens are never logged. `cmd/auth` mirrors `cmd/akira-server` (godotenv, own `newLogger`/`fatalf`, http.Server with timeouts, no graceful shutdown); the bootstrap user (`AUTH_BOOTSTRAP_*`) is created verified **with a connect_key**, and a taken username/email is only tolerated when the existing account matches the configured password and email — a mismatch (squatting) or a taken email is fatal at startup; an existing bootstrap account missing its verification or connect_key is healed. `httpapi_test.go` verifies a token end-to-end the way a downstream service would (fetch JWKS → `jwt.Parse` with `WithKeySet`), and covers the register → verify (tokens) → attempt exhaustion → resend → `/me` → regenerate flow plus the failure modes (oversized bodies, store outages mid-flow keeping one-time state intact). `oauth_test.go` covers the full authorization-code flow the way mcp-go's client drives it (metadata → dynamic registration → authorize → confirm → form-encoded token exchange with PKCE), incl. code replay, wrong verifier, foreign client_id, plain-PKCE rejection and anti-enumeration in `/authorize/confirm`.

MCP interface — `internal/akira-server/mcp` (package `akiramcp`, built on `mark3labs/mcp-go`), the layer an LLM talks to; served by `cmd/akira-server` as a **second HTTP listener** (port 7000, stateless JSON-RPC POST at `/mcp` via `NewStreamableHTTPServer(WithEndpointPath("/mcp"), WithStateLess(true))` — no sticky sessions, safe behind nginx). Dispatch goes straight to the in-process pool (`pool.SendTask`) — no proto changes. `New(Config)` returns a root mux: `/mcp` behind the auth middleware, plus `/.well-known/oauth-protected-resource/mcp` (RFC 9728 via mcp-go's `NewProtectedResourceMetadataHandler` — **public, no auth**; the `resource` is `MCP_PUBLIC_URL`/mcp, `authorization_servers` is `[MCP_AUTH_SERVER_URL]`). This is the standard OAuth entry point for MCP clients: an unauthenticated `/mcp` call gets 401 with `WWW-Authenticate: Bearer realm="akira", resource_metadata=<PRM url>`; mcp-go's client fetches the PRM, discovers the auth server, dynamically registers (`/oauth/register`), runs the authorization-code + PKCE flow and retries with the Bearer token.

- **`auth.go`** — `TokenValidator`: validates the auth service's RS256 access JWTs from `Authorization: Bearer` the way an external consumer would (`jwt.Parse` with `WithKeySet(cached JWKS, jws.WithRequireKid(true))`, `WithValidate`, `WithIssuer`; then `sub` non-empty and claim `typ="access"`). The JWKS cache is lazy — auth being down at startup is not fatal; an unknown `kid` (auth restarted, keys are in-memory) triggers a re-fetch, rate-limited to once per 30s so crafted unknown-kid tokens can't DoS auth (jwx has no typed error for "kid not in set", the match is on the error text). 401 + `WWW-Authenticate: Bearer` (with `resource_metadata`) on failure; on success the user_id from `sub` is put into the request context.
- **`tools.go`** — tool **`exec`** (args `client_id`, `cmd` required, `timeout_ms` optional, capped to `MCP_TASK_TIMEOUT_MS`) and tool **`write_file`** (`client_id`, `path`, `content` required, `create_dirs` default true). Shared `dispatch`: rejects a `client_id` containing `:` (it would forge another user's `connection_id`), builds `connection_id = {userID}:{clientID}`, calls `pool.SendTask`; `ErrConnectionNotFound` → "client not connected", `ErrConnectionClosed` → "connection lost", non-OK results formatted with status/exit_code/stderr as tool errors.
- **`resources.go`** — static resource **`akira://machines`** (JSON array of `{client_id, hostname, platform}` from `pool.ClientsByUser`) and template **`akira://file/{client_id}/{+path}`** (reserved expansion, so multi-segment paths work): dispatches a `read_file` task with `MaxBytes`/`TimeoutMs` limits, returns UTF-8 content as `TextResourceContents`, binary as `BlobResourceContents` (base64). Template variables arrive from mcp-go in `request.Params.Arguments` as **[]string** — `argString` normalizes.
- **`server.go`** — `New(Config)` assembles the MCPServer + tools + resources and returns the root mux (auth'd `/mcp` + public PRM endpoint) wrapping the streamable handler in the auth middleware. Tests: `auth_test.go` (real token manager's JWKS over httptest), `mcp_test.go` (full JSON-RPC over httptest with a fake pool client, incl. 401s with `resource_metadata`, the public PRM endpoint, **user isolation** — a token of user B sees an empty machine list and cannot exec on user A's machines), `e2e_test.go` (real gRPC server + real `akira-client` + real executor: write → read from disk → resource read → `exec cat` over MCP).

Key invariants when modifying either side:

- Only one goroutine may call `stream.Send` per stream (gRPC streams don't allow concurrent sends). On the server all outgoing messages go through a channel to a single writer loop — `ClientConnection.Post` → `Out()` → the loop in `Connect`. The client stream is server→client only, so the client never sends on it. The `out` channel is never closed — closing it would make a concurrent `Post` panic on "send on closed channel"; termination is signalled via `done` only.
- `pending` map in `ConnectionPool` correlates `task_id` → pending entry between `SendTask` (sender side) and `HandleResult` (fed by `SubmitResult`); entries are owned by `connection_id`. Waits do **not** survive disconnects: when the connection is lost, `failPendingClient` fails every pending task of that connection with `ErrConnectionClosed` (reconnects don't re-send tasks, so a timeout-less task whose client never returns would otherwise wait forever). Exception — the reconnect race: if `Unregister` finds a newer connection already registered, only the old connection's unsent queue messages are failed (`Close` → `failUnsent`); the client is back, so its already-sent tasks may still deliver results. Results for unknown `task_id` (server-side timeout already fired, or the wait was failed on disconnect) are discarded silently; results stamped with a non-owner `connection_id` are rejected and the wait continues.
- On disconnect `Unregister` runs; a client reconnecting with the same `connect_key` + `client_id` (hence the same `connection_id`) while the old stream is still registered gets `ErrAlreadyRegistered`. Half-open (silently dead) old registrations are cleared by the server-side keepalive (~80s), not by heartbeats — the server never tracks heartbeat times.
- Task execution on the client is decoupled from the stream: each task runs in its own goroutine (`runTask` → `executor.Execute`), so a disconnect never interrupts a running task; finished results go to the outbox and are retried via `SubmitResult` (including after a reconnect — the server then discards them silently if the wait was already failed). `connection_test.go` in `internal/akira-client/connection` covers this (echo task, disconnect fails the pending wait while the task still completes, reconnect with same id); `pool_test.go` in `internal/akira-server/connection/pool` covers the failure paths (unsent task, task lost with the connection, duplicate id, timeout semantics, non-owner rejection).

## Conventions

- Comments and doc comments are written in Russian.
- Directories are lowercase, but package names may be longer than the directory (`pool` dir → package `connectionpool`, `server` dir → `connectionserver`), so imports use aliases named after the package.
- Server logging is `log/slog` (`slog.Default()` with a `component` field); the client uses stdlib `log`.
